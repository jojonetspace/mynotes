## 一、仍有价值、且明确没做完的（优先级高）

1. Standard.cshtml 的 methods 块还有约 1300 行 模板已经拆得差不多了，但 `methods`（805 行往后约 1360 行）和 `computed`（约 260 行）这坨 JS 逻辑还集中在主组件里。记忆里也明确记着"批发价面板（WholesalePrice）已有组件但未完全解耦"——这是上次重构列出但没收尾的 TODO。继续按面板职责把 methods 里成块的逻辑下沉到对应子组件，是延续既有方向、风险最低的一笔。

2. 列表页促销价回填的性能隐患（2026-09-23 记录的根因还在） 记忆里记得很清楚：多规格款展开子行时，`LoadSkusForListing → FillSkuPromotionForListing → DiscountActivityService.LoadActivities → LoadActiveActivitiesByShops(loadItems=true) → FillActivityItems → FillItemShopInfo` 会全量反查商品带 SKU，实测 items=23979 时耗时 9 秒。当时标注的是"补漏"，建议确认这个全量反查是否已彻底消除，没有的话这是实打实的用户可感知卡顿。

3. 发布校验不触发 form.validate() 的缺陷 记忆记录 `doSave` 发布时只跑 `validateItem + validateItemData` 纯数据校验，不触发表单级 `form.validate()`，导致像 `validateLogistic` 这种自定义 validator 发布时不执行。这个要确认是否已修——如果没修，属于会导致"前端放过、后端拦截"的体验问题，且和前后端校验对称那条红线相关。

## 二、结构性优化（中等优先级，收益明确但动得多）

4. 多平台商品面板的重复 `Active/` 下 TikTokProductPanel（926 行）、ProductPanelBase（842 行）、ShopeeProductPanel（478 行）各一套。既然已有 ProductPanelBase 基类，值得盘一下三个平台面板里是否有可以继续上提到基类的公共模板/逻辑，减少平台新增时的复制成本。这正好和 listing-platform-adapter Skill 想降低的"新平台接入成本"是一个方向。

5. 组件实例复用导致的状态残留 记忆里有个已知 bug 根因：ItemCreator 切换商品时复用同一个 Standard 组件实例，只更新 itemInfo 不重置子组件状态，导致过 Lazada 的 `lazadaPromotion` 残留。目前靠 `rulesLoaded` 门控等补丁在打。可以评估是否用 `:key` 强制重建、或建立统一的 `reset()` 约定，从机制上消除这类"切换残留"隐患，而不是每出一个字段补一次。
